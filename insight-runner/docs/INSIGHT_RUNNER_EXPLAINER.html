Semaphor Architecture, Illustrated

The Insight Runner

A typed analysis agent that converts a Markdown briefing into a grounded, evidence-backed report. Plans tool calls, executes governed MCP queries, recovers missing answers, renders to Markdown / HTML / PDF, and delivers across Slack and email. Lives in semaphor-report-scheduler/insight-runner.

01. Mental model

The insight runner is an agentic loop with a typed, repairable spine. A user (or scheduler) submits a Markdown briefing definition; the runner converts it into typed slots, lets a model plan governed MCP tool calls, watches which slots are answered by evidence, runs a bounded recovery pass for the unanswered ones, then synthesizes, renders, and delivers a report.

In One Sentence
A Briefing is a set of typed answer slots. The runner uses a model to plan governed MCP tool calls against Semaphor, collects results into an evidence ledger, loops recovery for unanswered slots, then synthesizes, renders, and delivers a report.
Contracts first

Slots are the truth

Coverage flows through typed AnswerSlotExecutionResult, not from prose or the evidence ledger. The ledger is audit data.

Governed

Through MCP, not raw SQL

All queries go through Semaphor MCP: semaphor_analyze by default, semaphor_query_sql_advanced when bounded SQL is justified.

Bounded

Budget & policy

Every iteration enforces a tool whitelist, SQL bounds (LIMIT required), briefing scope policy, and a finite maxToolCalls.

04. The eleven phases of a run

A request flows through the same eleven phases regardless of entry point. Each phase emits trace events and may push entries into the evidence ledger.

Eleven phases, four lanes. Three model calls (normalize, plan-per-iteration, synthesize) bracket the deterministic and policy-bounded work.

06. The insight loop — why it iterates

The single most important question about this runner is: why is planning a loop, not a single model call? The short answer is that the model cannot plan everything up front, because most of the information it needs to plan does not exist yet. Each iteration gives the model a fresh, richer view of reality and asks for the next small batch of moves.

Mental model: this is a bounded ReAct loop. The model acts as a planner, not an executor. It proposes a small batch of tool calls, the runner executes them through policy, evidence and coverage update, and the loop hands the model the new state for the next batch. Five iterations + a budget of tool calls give meaningful depth without unbounded cost.

What the model doesn't know on iteration 1

Briefings start from a Markdown definition and a project token. The planner doesn't yet know any of this:

  • Which semantic datasets exist in the project
  • What fields they have, what role each field plays
  • Whether a candidate dataset name in a slot actually resolves
  • Whether requested metric/dimension fields exist or are calculated
  • What the real time-window of available data is
  • Whether previous_period comparison returns rows
  • Whether a query will succeed, partially succeed, or error with a recovery hint
  • How many tool calls are left in the budget

What changes between iterations

These five inputs to model.createPlan() all change as the loop progresses. That is the leverage iterations buy.

InputHow it evolves
evidenceEach successful tool call adds an entry: schema, query result samples, query path decisions. The model can now reference real field names.
answerCoverageRecomputed at the top of every iteration. Slots transition from missing_schema → missing_query → partial → answered. Tells the model what is still missing.
remainingToolCallsDecreases monotonically. Tells the model how aggressive to be: do a careful schema pass when there's budget; commit to the best guess when there's not.
policy violationsIf the previous batch had calls rejected (bad SQL, out-of-scope, duplicate), the violations show up in evidence as limitations. The model gets one chance to correct.
recovery hintsFailed query results often carry { invalidField, candidates: [...] }. Stored in evidence; the next plan can use the candidate instead of guessing again.

A single iteration, in detail

Six steps per iteration. The model proposes; policy gates; the runner executes; evidence and trace persist across iterations.

What a model plan looks like

{
  summary: "Discover sales domain, then query monthly revenue trend",
  rationale: "Need schema before issuing a metric query",
  recommendedQueryPath: "query_spec",
  plannedToolCalls: [
    {
      name: "semaphor_list_datasets",
      arguments: { domainId: "sales" },
      purpose: "[slot:revenue_trend] discover orders dataset"
    },
    {
      name: "semaphor_analyze",
      arguments: {
        domainId: "sales",
        datasetName: "orders",
        metrics: [{ name: "revenue", datasetName: "orders" }],
        dateField: "order_date",
        timeGrain: "month",
        comparison: "previous_period"
      },
      purpose: "[slot:revenue_trend] monthly revenue with YoY comparison"
    }
  ]
}

The [slot:X] tag in purpose is what coverage assessment uses to attribute evidence back to answer slots.

The five exit conditions, in priority order

The loop has more ways to terminate than it has ways to continue. Understanding each one is how you debug a Briefing that "ran but didn't answer."

Trace eventCondition (checked in this order)
tool_budget_exhausted At the top of the iteration, remainingToolCalls ≤ 0. The hard ceiling. maxToolCalls defaults to a finite value per run.
planning_paused_for_answer_recovery If the AnswerContract has slots, the loop reserves 6 tool calls for the kernel recovery phase. Once remainingToolCalls ≤ 6 on iteration 2+ AND coverage is incomplete, planning yields its remaining budget to recovery.
planning_complete The model returned plannedToolCalls: []. That's the agentic "I'm done" signal. Coverage may or may not be satisfied; if not, recovery still runs.
planning_stalled (no-progress) executedThisIteration === 0 && !feedbackThisIteration. Every planned call was a duplicate, but no policy violation triggered either. Loop bails immediately.
planning_stalled (feedback-only) Two consecutive iterations where the only output was policy feedback (consecutiveFeedbackOnlyIterations ≥ 2). The model got one chance to course-correct; it didn't. Bail.

The stall detector, mechanically

A subtle but important state machine. Two flags interact: executedThisIteration (did anything actually run?) and feedbackThisIteration (did the policy reject at least one call, OR did execution skip a duplicate?). They produce four cases:

The two-iteration grace period exists because the model deserves exactly one chance to fix policy-rejected calls after seeing the violation. Repeated feedback-only iterations mean the model can't recover.

Budget reservation, illustrated

Why does planning yield 6 tool calls to recovery? Because the recovery phase itself spends one tool call to ask the kernel for a plan, then executes up to ~5 returned recovery calls. Without the reservation, an over-eager planner could leave recovery with nothing to spend.

Reservation only activates on iteration 2+ and only when coverage isn't already satisfied (no point reserving if there's nothing to recover).

07. Tool call policy — the safety gate

Between the model and MCP sits applyPlannedToolCallPolicy(). It rejects calls that violate the read-only whitelist, lack required SQL bounds, fall outside briefing scope, or duplicate a previous call.

Five filters between the model's wishes and MCP. Each violation becomes a trace event so debugging is contract-shaped, not log-archaeology.

Read-only tool whitelist

Discovery (metadata, no rows)

  • semaphor_get_analysis_context
  • semaphor_list_semantic_domains
  • semaphor_list_datasets
  • semaphor_get_dataset_schema
  • semaphor_list_connections
  • semaphor_list_databases / _schemas / _tables
  • semaphor_get_dashboard_analysis_context

Query execution (returns rows)

  • semaphor_analyze — governed analytics; the default path
  • semaphor_query_sql_advanced — bounded read-only SQL; must include explicit LIMIT

Recovery kernel

  • semaphor_plan_analytics_recovery — the recovery-planning seam (see section 08)

No write tools, no schema mutations, no dashboard editors. Anything outside this list is silently filtered.

08. Answer contract recovery — the kernel-call pattern

When the planning loop exits with required slots still unanswered, recovery kicks in. Recovery planning is a shared MCP kernel tool semaphor_plan_analytics_recovery hosted in Semaphor App; the runner is a thin client. Field matching, dimension selection, period-change semantics, and dialect handling live in one place that MCP, App Builder, and dashboard assistants all reach.

Two MCP calls per attempt at minimum. First the runner asks the kernel for a plan (the kernel call itself counts toward the tool budget). Then it executes each call the kernel returns. Budget is reserved during planning — see the "Budget reservation" illustration in section 06.

Recovery is bounded and slot-targeted. The app-owned semaphor_plan_analytics_recovery kernel owns the planning seam; the runner adapter only builds typed operation intent and executes returned MCP calls.

09. Evidence ledger — the audit trail

Every tool call, query path decision, and limitation gets recorded in EvidenceLedger as an EvidenceEntry with a stable id (ev_001, ev_002, ...). This is audit data, not the source of truth for coverage.

EvidenceEntry shape

{
  id: "ev_004",
  type: "tool_call",
  summary: "Monthly revenue trend",
  toolName: "semaphor_analyze",
  purpose: "[slot:revenue_trend] ...",
  call: { ... },         // redacted
  resultSummary: { ... },
  recoveryHints: {
    invalidField: "order_dt",
    candidates: ["order_date"]
  },
  query: {
    queryPath: "semaphor_analyze",
    domainId: "sales",
    datasetName: "orders",
    rowCount: 12,
    analyticsIntent: { ... },
    analyticsExecutionResult: { ... }  // typed SemaphorAnalyticsExecutionResult
  },
  createdAt: "2026-05-21T..."
}

The analyticsExecutionResult field carries the typed execution envelope (status, validation issues, result shape) that AnswerCoverage reads as the source of truth. Plain evidence text is a fallback only.

Three entry types

tool_call

Recorded by recordToolCall({ call, result, purpose }). Extracts recovery hints from errors (invalid field + valid candidates) and query evidence from the result body.

query_path_decision

Model's explicit recommendation of which path to use next. recordQueryPathDecision({ queryPath, rationale }).

limitation

Constraints, errors, missing capabilities. recordLimitation(summary).

Snapshot & redaction

ledger.snapshot({ deliveryIntent }) returns an immutable EvidenceLedgerSnapshot. Before any callback to Semaphor App or external delivery, redactSecrets() strips tokens, connection credentials, and unbounded raw rows.

Coverage rule: the AnswerSlotExecutionResult is the typed coverage boundary. The evidence ledger is durable audit data, not the basis for "did we answer the user."

11. Report blocks & rendering

After synthesis, buildReportPlan() turns evidence + findings into a typed sequence of ReportBlocks. Three renderers consume the same plan: Markdown (canonical), HTML (themed), and PDF (Puppeteer).

One typed ReportPlan; three renderers. Markdown is canonical; HTML and PDF derive from a typed ReportDocument intermediate.

The eleven report block kinds

findings

Model-authored narrative with evidence refs.

evidence

Audit-formatted entry list.

query_summary

Query-shaped evidence with paths and parameters.

metric

title, value, secondary, delta, sentiment.

chart

Currently bar; data array of label/value.

progress

title, value (0..1), label, detail.

table

"business" or "evidence" presentation, columns + rows.

sql

Rendered SQL with title (for transparency).

limitations

Things the runner could not do.

next_actions

Suggested follow-ups.

delivery_intent

Free-text from the briefing definition.

kpi_grid

Tile grid emitted for consecutive metrics; uses table + border-spacing for cross-client email support.

Semaphor App owns the channel projection. The runner emits a logical BriefingContentDocument of these blocks. semaphor-app/src/lib/briefings/content-renderer.ts compiles it into the Markdown / HTML / email bodies, and slack-message.ts compiles it into Slack-supported primitives. Both adapters handle every block kind above; evidence_appendix and sql are gated by presentation.includeEvidence / includeSql flags on the briefing config.

12. Delivery

The runner doesn't open SMTP or call Slack itself for production; it produces a normalized delivery plan and either previews it (dry-run) or hands it off. The delivery intent string from the briefing definition is parsed for email addresses, Slack targets, and format hints.

Modes

summary

Short markdown body. Truncated to 1200 chars for previews.

pdf

PDF attachment only.

summary_and_pdf

Both: inline summary with PDF attached.

Channel boundary rules

Duplicates first. The canonical content document must be free of duplicate findings before any channel-specific delivery adapter runs. Slack adapter formatting concerns (block kit compatibility, parent/thread split) are downstream of that. A coherent artifact + a duplicating delivery adapter is still a bug.
No provider blocks leak into content. Delivery projection compiles structured content into the channel's supported primitives. Emitting raw Slack block kit (or anything provider-specific) from the content pipeline is the failure mode behind invalid_blocks errors.
Evidence and SQL are artifact controls. presentation.includeEvidence adds a canonical evidence appendix block. presentation.includeSql adds canonical SQL blocks for query evidence. Markdown and HTML render those blocks; Slack intentionally omits them from the parent/thread body and links back to the briefing/artifact instead.

15. Terminal status & the final payload

Every run ends in one of two top-level statuses for the BriefingRunnerResultPayload returned to Semaphor App, and in one of three logical states for the user-facing artifact.

ANSWERED

SUCCESS · complete

All required answer slots have answered execution results, presentation blocks satisfied, no duplicates. Payload status SUCCESS.

PARTIAL

Required slots answered but some presentation slots missing (e.g., requested chart kind not supported by selected artifact format). Payload status SUCCESS with warnings.

FAILED

Required slot unsatisfied after recovery, grounding empty, MCP preflight failed, or planning stalled. Payload status FAILURE with a concise terminal artifact, not a long limitations-heavy pseudo-report.

BriefingRunnerResultPayload shape

{
  status: "SUCCESS" | "FAILURE",
  title: "Q3 Revenue Briefing",
  summary: "Revenue grew 8% MoM driven by Enterprise...",
  artifacts: {
    markdown: "# Q3 Revenue ...",
    html: "<article>..."
  },
  evidence: { entries: [...] },     // redacted
  trace: { ... },                       // decoded token + events
  warnings: [],
  limits: {
    queryPath: "query_spec",
    bodyType: "markdown",
    maxToolCalls: 20
  }
}
The principle. Coverage flows through typed AnswerSlotExecutionResult, not from prose or the evidence ledger. The runner is allowed to fail loudly with a concise terminal artifact; it is not allowed to ship a long limitations-heavy report and call it success.

16. Server-side counterpart — the analytics kernel

Every MCP call the runner makes lands in semaphor-app. The MCP layer there is thin: tool definitions are per-domain registrars, and the analytics logic those tools depend on lives in a shared src/lib/analytics/ kernel. The runner is one client of that kernel; MCP is the surface it sees.

Why this matters for the runner: when the runner asks semaphor_analyze or semaphor_plan_analytics_recovery for something, that logic is reusable. The same kernel backs the data-app SDK route, dashboard assistants, and any other consumer that lands on MCP. A runner bug fix that strengthens the kernel benefits all of them; a runner-local hack benefits none.

What this means for runner contributors

  • Need a new shape of governed analytics? Extend src/lib/analytics/kernel/ and the corresponding service, then expose it through a MCP tool registrar in src/app/api/mcp/tools/. Do not assemble it in the runner.
  • Need a new recovery shape (different obligation kind, different recovery branch)? Extend src/lib/analytics/recovery/planner.ts and its test. Runner just sends the new SemaphorOperationIntent.
  • Need a new MCP tool entirely? Pick the registrar file by domain (query, grounding, dashboard, etc.), or add a new registrar and wire it into tools.ts.
The architectural shape the protocol explainer describes is now visible in code. MCP tools are adapters over a kernel; the kernel is one folder; the runner is an MCP client.
